# データフローの設定と公開

[FlowPorts 0.5.3](../../README.ja.md) · [Docs](../index.md) · [Website](https://flowport.pages.dev/ja/docs/)

未完成の下書きはソース、送信先、その容量割当が未設定でも保存できます。明示した容量は正数で合計予算内である必要があります。保存で収集は開始せず、稼働中の版も変わりません。公開には送信先と全割当が必要です。自動割当は公開時に確定し、送信先を追加しても手動割当は自動再配分されません。

公開後は実行ビューの配信確認を使います。現在の版の適用、ソースの準備、最新レポート、滞留の解消を待ち、確認を開始してから上流の実データを送信します。対応する HTTP と DataKit ソースでは公開済み Token に置き換える接続例をコピーできます。新規受信バッチ、正常処理バッチ、全送信先の確認増分を比べます。各ルートに一致するサンプルを送り、下流で内容を確認してください。自動送信や個別レコードの追跡は行いません。古いレポートや切断中は配信を判定できません。版、Worker 割当、プロセス、カウンターが変わったらやり直します。再読み込みや範囲変更でもリセットされます。プロトコルの応答は下流の業務処理完了を意味しません。

> **0.5.0 のポリシー変更：** 以下の「保持・再試行」は新しいチャネル上限（既定 5 回）までです。上限到達で未確認データを自動破棄し、最低 60 秒待機後に 1 バッチを試送信します。過去回数は保持します。関連する全ノードをプロトコル v8 に更新してください。[配信ポリシー](https://flowport.pages.dev/ja/docs/delivery/)を参照。


編集画面と実行ビューの上部にデータフロー ID とコピー操作を表示します。ログイン済み管理者は受信トークン（Vector を含む）を明示的に表示、非表示、コピーできます。下書きと公開済みの認証情報は別で、下書きの変更は公開して Worker が適用した後に有効です。トークンは実行ビューの集計範囲でのみ表示でき、個別 Worker 選択時には表示しません。他の上流認証情報はマスクされます。通常の参照とエクスポートは引き続き秘匿され、API Key と MCP では受信トークンを取得できません。

最初の公開前は Overview から最初のフロー作成または設定の続行に進めます。テンプレートはソース設定から開き、スクリプトとサンプルを保持します。変換が不要なら送信先へ進み、必要なら任意の処理ルールを追加します。フロー内で送信先を追加すると自動選択され、ソース設定やスクリプトは保持されます。

現在のフローを指定したプレビューは設定した measurement（既定は Source タイプ）と実行時の source_type、collectway_flow タグを使用します。サンプルはデコード後のソースレコードを表す必要があります。プレビューは上流へ接続せずデータも送信しません。

集計には最新の公開設定を表示し、Worker を選択するとそのノードにインストールされたパイプラインを表示します。公開とインストールの状態は別々に示し、未送信データの件数には過去のバージョンも含みます。

エディターは未保存の変更を示し、保存中や公開中には進行状況を表示します。公開後は実行ビューを直接開き、設定の適用状況、Worker のバージョン、実際の送信を確認できます。フロー一覧の操作は「受信を停止／受信を再開」です。受信を停止しても未送信データの処理と配信は継続します。送信先の障害で受信が自動停止することはありません。

エディター上部では「下書きを保存 → フローを公開 → Worker に適用」の手順を説明します。保存は変更の保持のみです。公開後は実行ビューで適用バージョンを確認し、実際の送信で到達を確認してください。送信先を保存すると参照フローと設定の適用状況が開き、各フローの下書きを確認して公開できます。送信先名だけの変更では再公開は不要です。 最後の送信先ステップの下部にも「保存して公開」があり、確認後にページ上部へ戻らず送信できます。保存や公開に失敗した場合は、上部に具体的なエラーを表示します。

フローは Source、種類別 Pipeline、既定送信先、任意の Tag 分岐、実行場所、キュー容量で構成します。公開は変更不能な版を作成して Worker へ非同期配布します。下書きは稼働版と独立です。保存前の接続テストは実行 Worker を選び、Pipeline のサンプルとは別に行います。[診断](https://flowport.pages.dev/ja/docs/#configure)を参照してください。

## Source と接続設定

名前、ID、Source 型/表示名でフローを検索します。新規作成内で収集方式と対応信号を絞り込みます。プッシュにはトークン/リスナー、消費にはキュー/トピックと認証、ポーリングには完全な URL が必要です。

高度な JSON は Source 全体の完全なオブジェクトです。コンテナのリスナーは通常 0.0.0.0 と公開ポートを使います。******** を保持すると同じ型の既存秘密を保存し、新値を入力して公開すると変更します。型変更では再設定が必要です。[Source](https://flowport.pages.dev/ja/docs/integrations/)を参照してください。

## 処理規則

ログ、指標、トレースなど種類ごとに独立したスクリプトを設定します。空は透過、DataKit は 15 種類に対応します。サンプル調整画面でデコード後 Point、出力、除外、型、Tag、原始 JSON を確認します。サンプルは下流に送信しません。入力・ソース・種類変更で旧結果は古いと表示し、閉じると編成に戻って入力と結果を保持します。[Pipeline](pipeline.md)を参照してください。

## 既定送信先と組み合わせ分岐

複数の既定送信先へ各 Point を複製し、独立確認・再試行します。異なる送信先は最大 32 個。送信先なしの下書きは保存できますが公開できません。

eq、neq、exists、not_exists と入れ子 AND/OR を使用します。最初の一致が既定集合を置き換え、未一致なら既定を使います。各規則は 1 つ以上の送信先を持ちます。常時保存する送信先は既定と各規則の両方に含めます。処理後 Tag を参照し、通常フィールドは set_tag で変換します。大文字小文字を区別し空白を自動除去しません。signals の除外で次規則へ進みません。[分岐](https://flowport.pages.dev/ja/docs/pipeline/)を参照してください。

現在の失敗処理と移行: [FlowPort](https://flowport.pages.dev/ja/docs/delivery/).

## 実行場所と容量

自動選択または許可 Worker を指定します。プッシュ/共有消費は複数ノード、ポーリング等は排他リースです。ネットワーク、TLS ファイル、クラウド認証は実行 Worker に必要です。

新規フローは Worker ごとに既定 256 MiB、内部 500 バッチを入力と各送信先へ固定割当します。ノードは既定 10 GiB、最大 10000 内部バッチで、予約と過去の使用量が収まる必要があります。物理ログとチェックポイントには別途空き容量が必要です。 受信確認はローカルの永続キューへの保存だけを示します。送信先ごとの再試行は初回を除き既定 5 回（0～100 回で設定可）です。上限到達後は未確認データを不可逆に破棄し、デッドレターや手動再送はありません。入力領域が満杯なら新規受信を拒否し、出力領域が満杯ならそのチャネル内だけで FIFO 破棄します。縮小時は既存の滞留を保持して解消を待ちます。処理失敗でも入力を解放する場合があります。公開成功だけでは Worker への適用や下流の受信を証明できません。下流の内容を確認してください。

## 保存・公開・版

下書き保存は編集だけ、公開は検証と新版配布、停止は新規入力停止、開始は最終公開版の再開です。送信先保存後は参照フローを再公開して新規入力に反映します。

同期中は希望版/導入版、Source 状態、エラーを確認してください。公開成功は収集証明ではありません。版衝突では再読み取りして統合し、未保存離脱には確認が出ます。

## 稼働図から設定

鉛筆で Source、Pipeline/種類、Tag 分岐、対応 Destination を開きます。クリックで保存や公開はしません。稼働図は公開版、編集は最新下書きです。戻ると Worker、アニメーション、スクロール、元のフォーカスを復元します。編集中は図の取得のみ停止し、実収集は続きます。遅れた応答は離脱後に編集画面を再表示しません。スクリプト一覧はキーボードでスクロールできます。

## 停止と削除

受信確認はローカルの永続キューへの保存だけを示します。送信先ごとの再試行は初回を除き既定 5 回（0～100 回で設定可）です。上限到達後は未確認データを不可逆に破棄し、デッドレターや手動再送はありません。入力領域が満杯なら新規受信を拒否し、出力領域が満杯ならそのチャネル内だけで FIFO 破棄します。縮小時は既存の滞留を保持して解消を待ちます。処理失敗でも入力を解放する場合があります。公開成功だけでは Worker への適用や下流の受信を証明できません。下流の内容を確認してください。

公開済みデータフローの ID は削除後も履歴上のリソース識別子として保持され、再利用できません。新しいフローには新しい ID を使用し、Worker のカーソル、リース履歴、カウンターを引き継いで初回収集を飛ばすことを防ぎます。同じフローの停止と再開は永続化された進捗から続行します。一度も公開していない下書きは削除後に ID を再利用できます。

下書きには独立した `draft_revision` があります。新規作成時は0、更新時は取得した `revision` と `draft_revision` の両方を送信します。保存すると新しい下書きバージョンが返ります。公開リクエストの本文には保存結果の `draft_revision` が必要です。省略は400、下書きの変更は409となり、別の編集者の変更を公開しません。Source のプロトコルを変更する場合は認証情報を再入力してください。フロー一覧の公開履歴ではページ切り替えと設定比較ができ、過去のバージョンを下書きに復元できます。復元だけでは実行中のバージョンは変わりません。確認後に通常の手順で再公開し、その時点の送信先のアドレスと認証情報を使用します。

削除済み Worker の過去の受信、送信、送信先のカウンターは一覧と実行画面で一貫して保持され、サンプルはオフラインとして表示されます。強制削除されたノードのキューが不明な場合、フローの削除は引き続き拒否されます。ノードが永久に失われた場合はフローを停止し、上流システムとロードバランサーからノードを外してから、フロー一覧のノード処置画面で削除済みノードを選択し、完全なフローIDを入力してください。`POST /flows/{id}/abandon-worker` に `worker` とフローIDと同じ `confirm` を指定します。このフローに対するそのノードの削除制限のみを解除し、ディスクと最終報告は変更せず、他ノードの排出確認も省略しません。判断は永続化され、強制操作として監査記録に残ります。`GET /flows/{id}/recovery` で確認できます。

現在の失敗処理と移行: [FlowPort](https://flowport.pages.dev/ja/docs/delivery/).


0.1.19 以降、送信開始後、応答前に FIFO で除去された分岐についても、実際の失敗または確認済みの成功を永続的に計数し、送信先の正常性を更新します。ペイロードの復元、除去回数の取り消し、受領位置の二重更新は行いません。同じ分岐が FIFO 除去と確認済み配信の両方に計上されるため、差し引いて一意の入力数を求めることはできません。有効な接続の遅延成功で、その送信先のアラートを解除できます。過去の公開接続の結果は現在の正常性を変更できず、削除済みで保留データのない送信先の遅延失敗はアラートを再作成しません。


## 0.1.21

参照フローを再公開し、Worker での適用を待ってください。同じ送信先 ID の滞留データは処理結果を保持し、次の再試行から新しい接続を使用します。送信中の旧リクエストは撤回できず、復旧時に重複する場合があります。

保存済みの送信先設定を比較します。未保存の編集は含めず、名前の変更は再公開不要です。最新接続を適用済みの Worker は次の再試行から使用します。送信中の旧リクエストは撤回できません。

破棄数は現在および直前 4 分のバケットで集計し、再起動後も保持します。時刻は元の受信時刻です。オフラインノードの最終サンプルから現在の保持時間は予測できません。

破棄数はローカル入力または送信先分岐の単位であり、一意の入力損失率には換算できません。送信先コピーとバッチ上限は保持範囲を短縮します。論理割り当ては実ディスクを予約しません。

現在の下書きと保存済み送信先の信号フィルターを最大 100 出力点で確認します。接続や書き込み権限の検証は行いません。未一致時は既定の送信先を使用し、フィルター後は次のルールに進みません。

設定を保存。参照フローを再公開してインストール後、新入力と同じ送信先 ID の滞留に新接続を適用。


## 0.1.24 のリソースと履歴の制限

各フローの最新 100 バージョンを、全暗号化スナップショット共通の 64 MiB 内で保持します。未参照の古い履歴から回収し、現行、通常／旧隔離キュー、送信中、管理側承認／Worker 報告の参照は保護するため件数を超える場合があります。保護対象だけで予算を満たすと新規公開は失敗し、既存の受付は続行します。更新前の超過参照は保持します。空になったフローの削除後は完全な履歴を回収し、ID の再利用を防ぐ最小情報を残します。復元対象は保持中の版のみです。実ディスクは通常のログ回収で解放し、旧失敗ペイロードを自動削除しません。 割り当て済みのリモート Worker は通常キューと旧失敗ペイロードが空になった後に削除済みフロー設定を回収し、オフラインのノードは再接続後に処理します。

現行版は制御プロトコル v8、チェックポイント形式 3 を使い、旧形式 1/2 を読み取れます。停止後、各ノードの全データ、master.key、Lookup、環境設定をバックアップしてから管理サーバーと全 Worker を更新してください。ダウングレードは更新前の完全なバックアップを復元し、その後の受信データを照合します。旧版で更新後のディレクトリを直接開いたり上書きしたりしないでください。

## シナリオテンプレートとフロー単位のインポート／エクスポート

新規フローから空白作成、シナリオテンプレート、設定のインポートを選べます。テンプレートは HTTP ログ転送、ログレベル別ルーティング、60 秒の重複排除、エラー前後のログ、ウィンドウ集約メトリクスを提供します。HTTP JSON ソース、スクリプト、サンプルが入力済みで、ソースは変更可能です。認証情報、送信先、Worker を設定し、Pipeline のサンプルデバッグで確認して保存・公開します。集約先は metric 対応が必要です。キャッシュとウィンドウは Worker、公開バージョン、入力種類ごとの有界メモリを使い、再起動で消去されます。

フロー一覧の設定エクスポートから、保存済み下書きまたは最新の公開済み設定を選んで JSON を取得します。未保存の編集は含まれません。形式は `format: "flowport.flow"`、`version: 1` で、ソース設定、種類別 Pipeline、既定／ルーティング送信先の参照、Lookup バインド、キュー容量、ACK ポリシーを含みます。共有送信先の接続、Lookup の内容や同期認証情報、Worker 配置、キュー、収集カーソル、公開履歴、メモリ状態は含まれず、完全バックアップの代わりにはなりません。

トークン、パスワード、headers、URL、接続文字列、秘密鍵などは再帰的に削除され、`removed_fields` に記録されます。スクリプト、SQL、カスタム設定のリテラル値はそのままなので、共有前に確認してください。インポートでも機密項目を削除し、`********` で以前の認証情報を復元しません。

インポート手順：

1. 移行先に必要な送信先と Lookup を作成し、Lookup データは別途アップロードまたは同期します。
2. 新規フロー → 設定インポートで最大 2 MiB の JSON を選択します。形式バージョン、Source タイプ、構造を検査し、概要と削除項目を表示します。
3. すべての既定／ルーティング送信先と Lookup 参照をローカルリソースに明示的に割り当てます。同名や同 ID での自動割り当て、共有リソースの作成・上書きはありません。
4. 名前、接続、認証、Worker、キュー容量、ルールを確認します。Lookup の自動更新方針と固定バージョンは保持されます。固定バージョンが選択リソースに存在し互換性があるか、Pipeline の Lookup パネルで確認・変更してください。
5. サンプルを実行し、新しい下書きとして保存して明示的に公開します。ファイル選択やエディターへの移動だけでは保存、受信開始、元フローの変更は行いません。新 ID を発行して公開・実行状態をリセットし、収集進捗は引き継がないため、消費型ソースの開始位置を確認してください。

REST: `GET /api/v1/flows/{id}/export?configuration=draft|published` は機密項目を除いたパッケージを返します（既定 draft）。`POST /api/v1/flows/import-preview` はパッケージ全体を受け取り、正規化設定と完全な依存一覧を返し、保存しません。依存を割り当て、新 Flow ID を設定して既存の下書き PUT と公開 POST を使います。既存の認証と 2 MiB の管理リクエスト制限が適用され、エクスポートは read、インポート確認は write が必要です。保存・公開は既存の監査対象です。MCP は `exportFlow` と `previewFlowImport`、シナリオテンプレートは UI で利用できます。[Pipeline の使用](pipeline.md)も参照してください。


インポート画面にはリソースの割り当て状況が表示され、内容をスクロールしても操作ボタンは表示されたままです。ファイルの確認中でもキャンセルやファイルの変更ができ、古い応答が新しい選択を上書きすることはありません。Lookup 一覧はこのダイアログを開いている間だけ再利用されます。読み込みに失敗した場合やリソースが変更された場合は、「リソースを更新」を選択してください。ファイルの再アップロードは不要で、概要と送信先の選択は保持されます。エクスポートダイアログを閉じると、未完了のダウンロード要求もキャンセルされます。

公開履歴では、現在の下書きと選択したバージョンのソース、Pipeline、Lookup バインディング、送信先、ルーティング、キュー容量、Worker 配置を比較します。復元で置き換わるのは下書きのみで、確認して公開するまで実行中の設定は変わりません。固定された Lookup データバージョンも確認してください。セッション失効後に再ログインしても、以前の作成ダイアログは自動で開きません。


エディター上部には ID、Token と主要操作を表示します。保存と公開の説明を開くと適用手順を確認できます。保存は下書きのみを更新します。公開後は Worker の導入バージョンと実際の配信を確認してください。


宛先やルートの設定前でもサンプルスクリプトを実行できます。処理結果を返し、ルートの検証エラーはプレビュー内で別に表示します。設定後に再実行してください。公開時の全設定検証は維持します。


Pipeline のデバッグ、接続診断、保存、公開は、開いたままの詳細 JSON を含む現在のソース設定を使用します。詳細 JSON が無効な場合は、以前の設定を使わずデバッグを停止します。


公開成功の通知は設定の保存を示します。Worker へのインストール完了は実行ビューの設定状態で確認してください。

## 固定容量の分離

編集画面のタイトルにはフロー名を表示し、未保存の変更、保存済み下書き、稼働中の設定を区別します。送信先ステップの「チャネル容量」には、全体予算、割り当て済み容量、入力と出力の固定枠をまとめます。各領域の行でバイト数とバッチ数を編集します。予算超過や固定枠の不足がある場合は公開できません。破棄や縮小の詳細ルールは展開して確認できます。

新規フローの既定は 256 MiB と 500 バッチです。保存済みのワークスペース既定値と明示的な配分は変更されません。固定容量分離のみをサポートします。宛先設定で `queue_capacity.input` と `queue_capacity.outputs` を割り当て、保存して公開します。新規公開で省略した場合、バイト予算と 500 バッチを入力と全宛先に均等配分し、編集画面も保存時に初期値を記録します。既存の明示的な配分は自動変更しません。新しい宛先には手動配分が必要です。単位は Worker × フロー × 宛先です。合計は `queue_bytes` と `queue_capacity.batches` 以内にし、予約と未移行の旧データはノードのバイト上限と 10000 バッチ以内にします。複数の既定フローがノードのバッチ上限を超える場合は、固定枠を明示的に減らしてください。自動では減りません。未配分の容量はチャネルに属さず、相互借用しません。

更新前に各 Worker のバックアップ副本で `collectway -queue-capacity-preflight -data-dir <Workerバックアップ副本> -queue-bytes <ノードのバイト予算>` を実行し、本番データディレクトリを直接指定しないでください。事前検査はメタデータによる推定であり、ペイロードの完全性や将来の割当は保証しません。旧版のバイト予算を保持し、Worker は既定 500 バッチで固定予約を試みます。既存の予約は再起動や今後の更新でも維持し、新しい宛先には明示的な割当が必要です。レコード数のない出力はロック外で最大 64 件・約 32 MiB ずつ読み、進捗を永続化します。容量不足、宛先不一致、読取不能時はデータを保持し、新規受信を停止します。上流のバッファ能力はソースに依存します。再起動前にメモリ上のウィンドウを排出してください。プロトコル v6 と v8 は互換性がなく、協調更新中は受信が中断する場合があります。公開成功は Worker へのインストールを意味しません。停止中のフローも予約を保持します。

旧データが既定の領域枠を超える場合、枠と使用量の大きい方を予約し、縮小後の排出状態になります。入力が超過中は新規入力を拒否します。出力が超過中は旧データを保持し、そのチャネルの新しい出力を破棄して集計します。事前検査は各領域の上限・使用量・実予約を表示し、ノードにはその予約を収容する容量が必要です。有効なフローが Worker から移動した場合、ローカルの滞留、送信中の要求、集約ウィンドウがすべて終わってから予約を解放します。再割当時には再予約します。全体で無効化されたフローは予約を保持します。 管理サーバーと対象 Worker の双方にこの修正が必要です。旧 v8 Worker は解放指示を無視します。準備の期限はペイロード読取の間に確認するため、1 回のディスク読取や永続化が期限を超える場合があります。

入力領域が満杯なら出力を削除せず、新規入力を拒否します。HTTP/gRPC は再試行可能なエラー、確認型ソースは未確認のまま保持し、UDP は破棄を集計します。DataKit、Firehose、CDC の要求／トランザクションは全体で原子的に受け入れます。カーソルメタデータ不足も入力を拒否し、古い受領票の全分岐を削除しません。

単一 WAL トランザクションで入力を除去し、宛先出力を追加して、チャネル内で元の受信順に破棄します。分割、複製、再試行、待機、送信中も容量を消費します。巨大な単一分岐は自身だけを破棄し、旧データを消しません。送信中は保護し、空きを作れない場合は新しい分岐を破棄します。容量による破棄は送信試行や成功に数えず、事前保存したレコード数を集計します。全分岐が終端になってからカーソルを順に進めるため、CDC でもデータ欠損はあり得ます。

縮小は既存データを即座に削除しません。新上限を超える間は排出中として、新出力を満杯時の扱いにします。使用量が減ってから予約を解放します。削除した宛先は旧入力、出力、送信中要求が完了するまで廃止処理中です。新宛先は明示的な割り当てが必要です。拡張や移行の事前検査失敗は旧実行設定を維持します。共有容量モードは提供しません。

実行詳細では Worker ごとに適用版、使用量、上限、実予約、最古時刻、容量破棄を表示します。容量状態は配信健全性から独立し、継続的破棄は直近 5 分の破棄を示します。送信成功で直ちに消えません。期限切れやオフラインの報告は最終報告と明記します。制御プロトコル v8 のため、管理サーバーと関連 Worker をすべて更新してください。管理サーバーの公開成功だけでは適用完了ではありません。

分離は論理容量と破棄範囲のみです。ディスク、CPU、ネットワーク、Store 書き込みは共有され、ディスク不足はノード全体の入力停止を招き得ます。再起動で容量、順序、試行数、履歴を保持します。

容量の適用状態は領域 ID と固定枠の値で比較し、JSON のキー順序には依存しません。適用値には送信先名を表示します。終了処理中のチャネルには引き続き保持中の固定枠を表示します。
