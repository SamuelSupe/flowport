# Lookup データ補完

[FlowPort 0.2.0](../../README.ja.md) · [使い方](https://flowport.pages.dev/ja/docs/pipeline/)

Lookup は管理・同期・バージョン管理ができるローカル照会リソースです。管理ノードが完全なスナップショットを取得して検証し、Worker は不変ファイルをダウンロードします。外部接続の資格情報は管理ノードだけが保持します。イベント処理時に外部サービスへ照会せず、追加のデータベースやスケジューラーも不要です。

2026-10-20 に隔離環境と合成データを使い、0.2.0 リリース候補の英語画面を撮影しました。この画面は 0.2.0 に含まれます。撮影時のビルド情報は画像マニフェストに保持しています。アドレスや件数は例です。画像を選択すると拡大できます。

## 設定と使用

Lookup ページでリソースを作成します。UTF-8 CSV、CSV.GZ、利用者提供の MMDB をアップロードするか、HTTP(S)、S3 互換 Bucket/Key、PostgreSQL、MySQL を選択します。CSV 列名は空でなく一意にし、値は文字列として扱います。照会テスト、同期状態、履歴、参照フロー、Worker の実際のバージョンを確認できます。

Pipeline パネルでバインドを追加し、自動更新または固定バージョン、Field/Tag 入力、照会列、出力マッピングを選択します。関数を必要なスクリプト位置に挿入します。バインド名は文字列リテラル必須です。同じ定義でマッピングを実行し、一致したかを真偽値で返します。通常どおり下書きを保存して公開します。

サンプル画面の Lookup ビューには使用バージョン、件数を制限した一致行、診断が表示されます。Lookup 自体はイベントを破棄しません。フィルターと振り分けには既存の Pipeline 条件と Tag ルーティングを使います。

左側でリソースを検索して選択します。「リソース設定」には選択したソースの項目だけを表示し、認証・TLS・詳細設定は折りたたみます。「照会をテスト」では列を選び値を入力し、結果と実際のバージョンを表で確認できます。「バージョンと状態」には履歴、Worker のインストール状況、参照フローをまとめます。同期間隔はプリセットまたは任意の秒数で指定できます。未保存の変更がある場合は移動時に確認し、保存してからアップロード・同期・ロールバックします。

長いフォームを編集中も保存操作を表示します。リソース作成後はアップロードまたは同期を次の操作として案内し、アップロード成功時と初回の手動同期後は照会テストへ移動します。保存済み接続先のアスタリスクは元の値を維持します。認証ヘッダーには空のオブジェクト、または値がすべて文字列の JSON オブジェクトを指定します。

| データバージョン | 自動更新 |
| 照合方式 | 完全一致 |
| 大文字と小文字を区別しない | チェックなし |

| --- | --- | --- |

| 出力列 | 出力種別 | 出力名 | デフォルト値 |

### 6. 結果に応じて振り分ける、または除外する

重要な業務のイベントを別の送信先に送るには、データフローの送信先ステップで「Tag で振り分け」を有効にし、次のルールを設定します。

| 条件 | 送信先 |
| --- | --- |
| Tag `level` が `核心` と等しい | 設定済みの重要業務用送信先 |
| ルールに一致しない | 設定済みのデフォルト送信先 |

振り分けは Pipeline 処理後の Tag を参照します。複数のルールがある場合は順に評価し、最初の一致を採用します。一致しない場合はデフォルト送信先を使います。サンプル画面のルーティングプレビューで選択された送信先を確認できます。詳細は [Tag の複合条件による振り分け](https://flowport.pages.dev/ja/docs/pipeline/) を参照してください。

### 7. 公開して検索データを更新する

サンプルを確認したら、ソースと送信先が設定済みであることを確認し、「下書きを保存 → データフローを公開」をクリックします。実行ビューで Worker が設定をインストールしたことも確認してください。サンプルデバッグはデータを送信しません。実際の配信は送信先の受領記録で確認する必要があります。

たとえば CSV の `payment` のチームを `交易平台组` に変更し、完全な CSV を再度アップロードします。

- バインドが「自動更新」の場合、各 Worker が新しいデータをインストールした後、新しく受信するバッチに新バージョンが使われます。フローの再公開は不要です。Worker 間では一時的にバージョンが異なることがあります。
- キュー内の既存バッチは受信時に固定したバージョンを使い続けるため、テーブルの更新で結果は変わりません。
- 固定バージョンのバインドは、選択済みのバージョンを使い続けます。選択を変更して再公開すると切り替わります。

「自動更新」はバインドがどのデータバージョンを使うかを決め、リソースの「自動同期」は外部ソースからいつデータを取得するかを決めます。ファイル / API はコンピューター上の `services.csv` の変更を監視しないため、再アップロードが必要です。定期的に更新するには、リソースのソースを HTTP(S)、S3、PostgreSQL または MySQL に変更し、列構成を保って「自動同期」を有効にします。Pipeline のバインドとスクリプトはそのまま使えます。同期に失敗した場合は、最後の有効なバージョンを使い続けます。

## 4 種類の照合

Exact は最大 4 キーの複合照合で、既定では大文字小文字を区別します。区別しない設定も可能です。重複キーは索引生成エラーになります。整数は十進文字列の精度を保ち、浮動小数点入力を暗黙変換しません。必要に応じ既存の変換関数を明示的に使います。

CIDR は IPv4/IPv6 に対応し、既定の最長プレフィックス、最初の一致、すべて一致を選べます。同じプレフィックスは表の順です。Regex は事前コンパイルした Go RE2 を使い、表の順に最初またはすべてを返します。先読み・後読み、後方参照、「最も具体的な正規表現」は非対応です。MMDB はデータベースの最長プレフィックスで IP を照会します。国・地域・都市・ASN・組織のプリセット、および `subdivisions.0.names.en` のような独自パスに対応します。

## 同期と完全性

既定は 15 分ごと、60–86400 秒で設定できます。即時同期も可能です。同一リソースは並列同期せず、管理ノード全体で最大 2 件、各 60 秒まで。失敗は次の周期に再試行します。HTTP は認証ヘッダー、TLS、ETag/Last-Modified に対応し、リダイレクトを追いません。S3 は指定オブジェクトだけ読み、オブジェクトバージョンを指定できます。バケット走査はしません。

SQL は読み取り専用アカウントと読み取り専用 Repeatable Read トランザクションで、セミコロンを含まない単一 SELECT を実行します。ページング、CDC、複数照会の連結はありません。整数と正確な数値は文字精度を保ちます。SQL の CIDR/Regex 表には、一意で非 NULL の整数型の順序列が必須で、全件読み取り後に数値順で並べます。中断・部分読み取り・上限超過は候補全体を無効化します。データベース関数もアカウント権限で制約してください。

取得、構造・稼働バインド互換性検証、索引生成、永続化、配布、Worker インストールの順です。同じ内容では新バージョンを作りませんが、確認成功時刻は更新します。空表は明示許可しない限り拒否します。欠落列、Exact 重複、無効索引、容量不足でも最後の有効版を維持します。2 周期成功確認がなければ期限切れ警告を表示し、ローカル処理は継続します。

## バッチと復旧

フロー設定版、Lookup データ版、バッチ使用版を分離します。自動更新でフローを再公開しません。Worker ごとに検証後、次のバッチ受理トランザクションで版を固定します。クラスター内の一時的な版の差は正常で、送信側は版を指定できません。同一バッチ、CDC 分割、クラッシュ復旧は同じ版を使い、処理済み送信滞留は保存した結果を再送します。

固定版は通常の公開で反映します。履歴版の有効化は自動同期を停止し、再開するには「リソース設定」で「自動同期」を有効にして保存します。初回有効版がなければ公開・開始を拒否します。キューに必要な版の欠落・破損は対象処理を停止して再取得し、ペイロードを保持します。リソース不可用を不一致や入力破棄可能な Pipeline エラーにしません。管理接続断でも完全なローカル版を利用でき、既存の非独占継続と独占所有リースを守ります。

## 制限とアップグレード

初期保護値は CSV/SQL 32 MiB・100000 行・64 列、Regex 1000 ルール・1 パターン 2 KiB・入力 64 KiB、MMDB 128 MiB、プロセス当たり候補・ロード・索引 256 MiB、ノード当たりファイル 1 GiB です。容量保証ではありません。解凍、構築、並列同期、参照中の旧版も含むため、ファイル上限前でも拒否し得ます。Pipeline の時間制限は継続します。

現在版、固定版、キュー、実行中、Worker に許可済みの版を保護し、未参照履歴を 5 件保持します。更新領域確保のため業務キューを破棄しません。メタデータは read、内容・試照会・変更は write 権限が必要です。資格情報は ********、監査に全内容や秘密を記録しません。通常管理要求は 2 MiB のままで、バイナリには独立した上限があります。MCP は管理・同期・試照会・状態、ファイル転送は REST を使います。

暗号化リソースは native/lookups/ に保存し、設定とキューは参照のみです。制御プロトコル **v6**、チェックポイント **形式 3** に全管理ノードと Worker を同時期に更新します。旧バイナリは新形式を拒否します。停止して全データディレクトリ・master.key・リソースをバックアップしてください。ダウングレードには更新前の完全バックアップが必須です。


Lookup の自動同期は操作者 `system` として監査に記録されます。Worker の状態には自動更新の選択バージョンと、固定バインディング・キュー用のインストール済みバージョンを表示します。出力マッピングには既存のバッチ出力上限 32 MiB を適用し、大きすぎる出力は割り当て前に拒否します。


Point のキー名は一意です。Field と Tag の間でも出力名を重複させることはできません。欠損補完では既存キーを保持し、上書き時は指定した種類で書き込みます。MySQL の一貫したスナップショットには InnoDB などのトランザクション対応テーブルが必要です。
