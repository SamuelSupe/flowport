# Lookup 데이터 보강

[FlowPort 0.2.0](../../README.ko.md) · [사용 안내](https://flowport.pages.dev/ko/docs/pipeline/)

Lookup은 관리, 동기화, 버전 관리가 가능한 로컬 조회 리소스입니다. 관리 노드가 전체 스냅샷을 받아 검증하고 Worker는 불변 파일을 다운로드합니다. 외부 소스 자격 증명은 관리 노드에만 저장합니다. 이벤트 처리 중 외부 서비스에 접속하지 않으며 별도 데이터베이스나 스케줄러 없이 단일 바이너리를 유지합니다.

2026-10-20에 격리 환경과 합성 데이터로 0.2.0 릴리스 후보의 영어 화면을 촬영했습니다. 표시된 화면은 0.2.0에 포함되며 촬영 빌드 정보는 이미지 매니페스트에 보존합니다. 주소와 수치는 예시이며 이미지를 선택하면 확대할 수 있습니다.

## 설정과 사용

Lookup 페이지에서 리소스를 생성합니다. UTF-8 CSV, CSV.GZ, 사용자가 제공한 MMDB를 업로드하거나 HTTP(S), S3 호환 Bucket/Key, PostgreSQL, MySQL을 선택합니다. CSV 열 이름은 비어 있지 않고 고유해야 하며 값은 문자열입니다. 조회 테스트, 동기화 상태, 버전, 참조 흐름, Worker별 실제 버전을 확인할 수 있습니다.

Pipeline 패널에 바인딩을 추가하고 자동 업데이트 또는 고정 버전, 명시적인 Field/Tag 입력, 조회 열과 출력 매핑을 선택합니다. 필요한 스크립트 위치에 함수를 삽입합니다. 이름은 문자열 리터럴이어야 합니다. 함수는 동일한 바인딩으로 매핑을 수행하고 일치 여부를 불리언으로 반환합니다. 초안을 저장하고 정상적으로 게시합니다.

{{code:0}}

샘플 작업대의 Lookup 보기는 실제 버전, 제한된 일치 행과 진단을 표시합니다. Lookup 자체는 이벤트를 버리지 않습니다. 필터와 분기는 기존 Pipeline 조건 및 Tag 라우팅을 사용합니다.

왼쪽에서 리소스를 검색하고 선택합니다. 리소스 설정에는 선택한 소스의 필드만 표시하며 인증, TLS 및 고급 옵션은 접어 둡니다. 조회 테스트에서 열을 선택하고 값을 입력하면 결과 행과 실제 버전을 표로 확인할 수 있습니다. 버전 및 상태에는 이력, Worker 설치 상태와 참조 흐름을 모았습니다. 동기화 주기는 기본 선택 항목이나 사용자 지정 값으로 설정합니다. 저장하지 않은 변경 사항은 이동 시 확인하며, 저장한 후 업로드, 동기화 또는 롤백할 수 있습니다.

긴 양식을 편집할 때도 저장 작업 표시줄이 보입니다. 리소스를 생성하면 다음 단계인 업로드 또는 동기화를 안내하고, 업로드 성공 또는 첫 수동 동기화 후 조회 테스트로 이동합니다. 저장된 연결 주소의 별표는 기존 값을 유지합니다. 인증 헤더에는 빈 객체 또는 모든 값이 문자열인 JSON 객체를 입력합니다.

### 3. Pipeline에서 리소스 바인딩

대상 데이터 흐름의 Pipeline 단계에서 로그 데이터 유형 `logging`을 선택하고 Lookup · 데이터 보강을 펼칩니다. 바인딩 이름에 `service_info`를 입력하고 바인딩 추가를 클릭한 뒤 아래와 같이 설정합니다.

| 설정 | 값 |
| --- | --- |
| Lookup 리소스 | `服务归属表` |
| 데이터 버전 | 자동 업데이트 |
| 일치 방식 | 정확히 일치 |
| 대소문자 무시 | 선택하지 않음 |
| 쓰기 규칙 | 누락된 값만 채우기 |

입력 키를 한 행 추가하여 이벤트의 일반 `service` 필드를 읽고 CSV의 `service` 열에서 조회하도록 설정합니다.

| 입력 유형 | 입력 이름 | 조회 열 |
| --- | --- | --- |
| Field | `service` | `service` |

실제 입력에서 `service`가 Tag라면 입력 유형을 Tag로 변경합니다. 일반 JSON 최상위 필드가 자동으로 Tag가 되지는 않습니다.

출력 매핑을 세 행 추가합니다. 각 행에서 기본값을 활성화하고 다음 값을 입력합니다.

| 출력 열 | 출력 유형 | 출력 이름 | 기본값 |
| --- | --- | --- | --- |
| `team` | Tag | `team` | `未归属` |
| `level` | Tag | `level` | `普通` |
| `cost_center` | Field | `cost_center` | `UNKNOWN` |

이후 라우팅에 사용할 `team`과 `level`은 Tag로, `cost_center`는 일반 필드로 기록합니다.

![Pipeline 바인딩이 service 필드를 읽고 조회 열을 team, business_level, cost_center Tag에 명시적으로 매핑합니다.](https://flowport.pages.dev/assets/screenshots/lookup-binding.webp)

*Pipeline 바인딩이 service 필드를 읽고 조회 열을 team, business_level, cost_center Tag에 명시적으로 매핑합니다.*

### 6. 결과에 따른 라우팅 또는 필터링

핵심 업무 이벤트를 별도 대상으로 보내려면 데이터 흐름의 전송 대상 단계에서 Tag 라우팅을 활성화하고 다음 규칙을 설정합니다.

| 조건 | 전송 대상 |
| --- | --- |
| Tag `level`이 `核心`과 같음 | 설정된 핵심 업무 대상 |
| 일치하는 규칙 없음 | 설정된 기본 대상 |

라우팅은 Pipeline 처리 후의 Tag를 읽습니다. 규칙이 여러 개라면 순서대로 평가해 처음 일치한 규칙을 사용하고, 일치하지 않으면 기본 대상으로 보냅니다. 샘플 작업 공간의 라우팅 미리보기에서 선택된 대상을 확인할 수 있습니다. 자세한 내용은 [복합 Tag 라우팅](https://flowport.pages.dev/ko/docs/pipeline/)을 참고하세요.

테이블에 존재하는 서비스만 유지해야 한다는 명확한 요구가 있다면 앞의 스크립트를 다음 스크립트로 바꿀 수 있습니다. 불일치 이벤트를 명시적으로 삭제하므로 일반적인 보강에는 필요하지 않습니다.

### 7. 게시 및 조회 데이터 업데이트

샘플 결과를 확인한 뒤 소스와 전송 대상이 설정되었는지 확인합니다. 초안 저장 → 데이터 흐름 게시를 클릭하고 실행 화면에서 Worker의 설정 설치를 확인합니다. 샘플 디버깅은 데이터를 전송하지 않으므로 실제 전달 여부는 대상의 수신 기록으로 확인해야 합니다.

예를 들어 CSV에서 `payment`의 팀을 `交易平台组`로 바꾸고 전체 CSV를 다시 업로드합니다.

- 바인딩에서 자동 업데이트를 선택했다면 각 Worker가 새 데이터를 설치한 후 새로 수신하는 배치부터 새 버전을 사용합니다. 흐름을 다시 게시할 필요는 없으며 Worker 간 버전은 잠시 다를 수 있습니다.
- 이미 큐에 들어간 배치는 수신 시 고정한 버전을 계속 사용하므로 테이블 업데이트로 결과가 달라지지 않습니다.
- 고정 버전 바인딩은 선택한 버전을 계속 사용합니다. 버전 선택을 바꾸고 다시 게시해야 전환됩니다.

자동 업데이트는 바인딩이 사용할 데이터 버전을 결정하고, 리소스의 자동 동기화는 외부 소스에서 데이터를 가져올 시점을 결정합니다. 파일 업로드 / API는 컴퓨터의 `services.csv` 변경을 감시하지 않으므로 다시 업로드해야 합니다. 주기적으로 갱신하려면 리소스 소스를 HTTP(S), S3, PostgreSQL 또는 MySQL로 변경하고 열 구조를 유지한 채 자동 동기화를 활성화합니다. Pipeline 바인딩과 스크립트는 그대로 사용할 수 있습니다. 동기화에 실패하면 마지막 유효 버전을 계속 사용합니다.

## 네 가지 일치 방식

Exact는 최대 네 개의 복합 키를 지원하고 기본적으로 대소문자를 구분합니다. 명시적으로 무시할 수 있습니다. 중복 조회 키는 인덱스 생성을 거부합니다. 정수는 십진수 텍스트 정밀도를 유지하며 실수 입력을 키로 암묵 변환하지 않습니다. 기존 변환 함수를 명시적으로 사용하세요.

CIDR은 IPv4/IPv6를 지원하며 기본값은 최장 접두사입니다. 첫 번째 또는 모든 일치도 선택할 수 있고 동일한 접두사는 테이블 순서입니다. Regex는 미리 컴파일한 Go RE2로 테이블 순서의 첫 번째 또는 모든 일치를 반환합니다. 전후방 탐색, 역참조, 가장 구체적인 정규식 모드는 지원하지 않습니다. MMDB는 데이터베이스의 최장 접두사 IP 조회를 사용하며 국가, 지역, 도시, ASN, 조직 프리셋과 subdivisions.0.names.en 같은 사용자 경로를 지원합니다.

기본값은 누락된 값만 채우기입니다. 빈 문자열은 기존 값입니다. 명시적 덮어쓰기와 출력별 기본값을 설정할 수 있습니다. 불일치는 원본을 유지하고 설정한 기본값만 적용합니다. 모든 일치는 테이블 순서대로 최대 64행이며 열마다 **JSON 배열 문자열**로 Field에만 기록합니다. Tag에는 기록하지 않고 Point 유형을 확장하지 않습니다. 초과 시 전체 조회에서 필드와 기본값을 기록하지 않고 false와 match_limit 진단을 반환합니다. 정규식 입력 초과는 regex_input_limit입니다.

## 동기화와 완전성

기본 주기는 15분이며 60–86400초로 설정하거나 즉시 동기화할 수 있습니다. 리소스별 병렬 실행은 없고 관리 노드는 최대 두 작업, 작업당 총 60초를 허용합니다. 실패는 다음 주기에 재시도합니다. HTTP는 인증 헤더, TLS, ETag/Last-Modified를 지원하고 리디렉션을 따르지 않습니다. S3는 지정한 객체만 읽고 객체 버전을 선택할 수 있으며 버킷을 검색하지 않습니다.

SQL은 읽기 전용 계정과 읽기 전용 Repeatable Read 트랜잭션에서 세미콜론 없는 단일 SELECT를 실행합니다. 페이지 분할, CDC, 여러 조회 조합은 없습니다. 정수와 정확한 수치의 텍스트 정밀도를 유지합니다. SQL CIDR/Regex 규칙에는 고유하고 NULL이 아닌 정수형 순서 열이 필수이며 전체 조회 후 숫자순으로 정렬합니다. 중단, 부분 읽기, 한도 초과 시 후보 전체를 폐기합니다. 데이터베이스 함수 동작도 계정 권한으로 제한해야 합니다.

전체 가져오기, 구조 및 실행 중 바인딩 호환성 검증, 인덱스 구성, 영구 저장, 배포, Worker 설치 순서입니다. 같은 내용은 새 버전을 만들지 않지만 성공 확인 시각을 갱신합니다. 빈 테이블은 명시적으로 허용하지 않으면 거부합니다. 누락 열, Exact 중복, 잘못된 인덱스, 용량 부족은 마지막 유효 버전을 유지합니다. 두 주기 동안 성공 확인이 없으면 오래된 상태 경고를 표시하되 로컬 조회는 계속합니다.

## 배치와 복구

흐름 구성 버전, Lookup 데이터 버전, 배치 실제 버전을 구분합니다. 자동 업데이트는 흐름을 재게시하지 않습니다. 각 Worker는 검증 후 다음 배치 수신 트랜잭션에서 버전을 고정하므로 클러스터 버전이 잠시 다를 수 있습니다. 송신자는 버전을 지정할 수 없습니다. 같은 배치, CDC 조각, 충돌 복구는 동일한 버전을 사용하고 이미 처리한 전송 적체는 저장된 결과만 재전송합니다.

고정 버전은 정상 게시로 적용합니다. 과거 버전 활성화는 자동 동기화를 중지하며 재개하려면 리소스 설정에서 자동 동기화를 활성화하고 저장해야 합니다. 최초 유효 버전이 없으면 게시 또는 시작을 거부합니다. 큐가 참조한 버전이 없거나 손상되면 관련 처리를 멈추고 다시 가져오며 페이로드를 유지합니다. 리소스 사용 불가는 불일치나 입력을 해제하는 일반 Pipeline 실패가 아닙니다. 관리 연결이 끊겨도 완전한 로컬 버전을 사용하며 기존 비독점 처리 지속 및 독점 소유권 임대를 따릅니다.

## 한도, 권한과 업그레이드

초기 보호 한도는 CSV/SQL 32 MiB, 100000행, 64열; Regex 1000규칙, 패턴당 2 KiB, 입력당 64 KiB; MMDB 128 MiB; 프로세스별 후보·로드·인덱스 예산 256 MiB; 노드별 파일 1 GiB입니다. 운영 용량 보장이 아닙니다. 압축 해제, 후보 구성, 동시 동기화, 참조 중인 구버전도 포함하므로 파일 한도 이전에 업데이트가 거부될 수 있습니다. Pipeline 실행 시간 예산도 유지됩니다.

현재, 고정, 큐, 실행 중, Worker에 허가된 버전을 보호하고 참조 없는 성공 이력 다섯 개를 유지합니다. Lookup 공간을 위해 업무 큐를 제거하지 않습니다. 메타데이터는 read, 내용·시험 조회·변경은 write 권한이 필요합니다. 자격 증명은 ********로 표시하고 감사에 전체 내용이나 비밀을 기록하지 않습니다. 일반 관리 요청은 2 MiB, 바이너리 업로드는 별도 스트리밍 한도를 사용합니다. MCP는 관리·동기화·시험 조회·상태를 제공하고 파일 전송은 REST입니다.

암호화 리소스는 native/lookups/에 별도로 저장하며 구성과 큐에는 참조만 저장합니다. 제어 프로토콜은 **v6**, 체크포인트는 **형식 3**입니다. 관리 노드와 모든 Worker를 함께 업그레이드해야 하며 이전 프로그램은 새 형식을 거부합니다. 중지 후 모든 데이터 디렉터리, master.key, 리소스 파일을 완전히 백업하세요. 다운그레이드는 업그레이드 전 전체 백업 복구가 필요합니다.


Lookup 자동 동기화는 `system` 실행자로 감사 기록에 남습니다. Worker 상태에는 자동 업데이트의 선택 버전과 고정 바인딩 및 대기열의 설치 버전이 표시됩니다. 출력 매핑은 기존 32 MiB 배치 출력 제한을 따르며, 너무 큰 매핑은 출력 메모리를 할당하기 전에 거부됩니다.


Point 키 이름은 고유합니다. Field와 Tag 간에도 출력 이름을 중복할 수 없습니다. 누락 값만 채울 때는 기존 키를 보존하고 덮어쓸 때는 지정한 대상 종류로 기록합니다. MySQL 일관된 스냅샷에는 InnoDB 같은 트랜잭션 지원 테이블이 필요합니다.
