# Pipeline 사용

[FlowPorts 0.5.3](../../README.ko.md) · [Docs](../index.md) · [Website](https://flowport.pages.dev/ko/docs/)

GuanceCloud Platypus Go 실행기를 사용하며 Vector VRL이 아닙니다. 소스, 캔버스, 바로가기 보기는 동일한 유형별 스크립트를 편집하며 .ppl 입출력을 지원합니다. 리소스 로딩 실패는 초안을 유지한 채 재시도합니다. 작업 영역은 최소 600px, 전체는 720px 이상이고 높은 창에서는 뷰포트 80%까지 확장하며 각 패널은 독립 스크롤합니다.

레코드당 실제 시간 예산은 100ms입니다. 수락된 입력 배치는 최대 3회 실행합니다. 처음 두 번은 입력을 유지하고 후보 상태를 되돌린 뒤 1초, 2초 대기합니다. 세 번째도 초과하면 해당 배치를 pipeline_error로 해제하고 처리 실패와 폐기 바이트를 기록합니다. 횟수는 재시작 후에도 유지되며 입력 당시 버전과 FIFO를 따릅니다. Worker 공용 바이트나 범위 수 부족은 입력을 유지해 재시도하고, 범위별 8 MiB 초과·파싱·타입·출력 오류는 입력을 해제합니다.

## 편집과 샘플

1. Pipeline에서 신호 유형을 선택합니다.
2. 소스를 편집하거나 함수, 할당, 조건, 반복 노드를 추가합니다. 모든 보기가 동기화됩니다.
3. 샘플 디버깅을 엽니다. 닫기/Escape는 입력과 결과를 유지하고 원래 위치로 돌아갑니다. 실행 중 닫기는 브라우저 대기를 취소하지만 시작된 서버 실행 중지를 보장하지 않습니다.
4. JSON 객체/배열을 입력하고 필요하면 정리 후 실행 또는 Command/Ctrl+Enter를 누릅니다. 최대 100개이며 하위에 보내지 않습니다.
5. 전후, 출력/필터 수, 이름, Tag, 유형과 나노초 시간을 확인합니다. 여러 출력/자식 Point 유형을 전환하고 단일 입출력의 추가/변경/제거 및 이전 값을 비교합니다.
6. 닫고 수정해 다시 실행한 다음 저장/게시합니다.

처리 전은 디코딩된 Point이지 원시 입력 JSON이 아닙니다. 원시 JSON 복사는 before/results의 숫자 텍스트를 보존합니다. 필드는 페이지당 50개이며 필터 수는 실행기 보고를 사용해 단순 입출력 차이가 아닙니다. 여러 결과는 위치로 대응시키지 않고 소요 시간은 네트워크를 포함합니다.

HTTP json/ndjson/text는 수집 형식이며 샘플은 JSON입니다. 큰 정수와 나노초 텍스트를 유지합니다. 정리와 백엔드 JSON 디코딩 모두 최대 64단계를 지원합니다. 입력/스크립트/유형 변경 후 결과는 오래된 표시가 되고 파싱/실행 실패를 수정해 재시도합니다.

## 버전 및 실패 해제

수신 확인은 로컬 영구 큐 저장만 의미합니다. 대상별 재시도는 최초 시도를 제외하고 기본 5회이며 0~100회로 설정할 수 있습니다. 소진 시 미확인 데이터를 영구 삭제하며 데드 레터나 수동 재생은 없습니다. 입력이 가득 차면 새 데이터를 거부하고 출력이 가득 차면 해당 채널 내에서만 FIFO로 제거합니다. 축소 시 기존 적체를 유지한 채 해소를 기다립니다. 처리 실패도 입력을 해제할 수 있습니다. 게시 성공만으로 Worker 설치나 다운스트림 수신을 증명할 수 없습니다. 실제 하위 내용을 확인하세요.

재시도는 원래 처리 결과, 대상 ID 및 전달 식별자를 유지합니다. 같은 대상 ID로 다시 게시하면 다음 전송 시도에서 새 연결 설정을 사용하며 Pipeline이나 라우팅을 다시 실행하지 않습니다. 새 게시 버전에서 대상을 제거하면 해당 분기는 이전 연결을 유지하고 다른 대상으로 보내지 않습니다. 카운터는 원래 입력 버전에 속하며 대상 저장이나 초안 편집만으로는 대기를 변경하지 않습니다.

processing_failed_batches는 입력 실패, 호환 이름인 sending_failed_batches는 재시도를 포함한 전송 실패 시도 횟수입니다. 전송 실패율은 실패 시도를 실패 시도와 sent_batches의 합으로 나눕니다. overflow_dropped_batches 및 overflow_dropped_bytes는 입력 또는 출력 분기의 FIFO 폐기를 따로 집계합니다. discarded_bytes는 처리 실패와 FIFO 폐기를 포함하며 보관된 전송 실패는 늘리지 않습니다. 수신, 폐기, 카운터 및 순서별 확인은 한 영구 트랜잭션으로 갱신됩니다. 저장 실패는 이전 데이터를 유지하고 새 수신을 확인하지 않으며 재시도는 확인을 완료하지 않습니다. 시작된 요청은 회수할 수 없어 폐기한 분기도 원격에 도달할 수 있지만 큐에 다시 나타나지 않습니다. 시간 초과와 충돌 중복은 여전히 가능합니다.

## Lookup

Lookup은 로컬 불변 데이터를 사용하며 배치별 버전을 고정합니다. 리소스가 없어도 큐 입력을 유지합니다. [Lookup](lookup.md)을 참조하세요. 현재 제어 프로토콜 v8와 체크포인트 형식 3은 조정된 업그레이드와 다운그레이드용 전체 사전 백업이 필요합니다.


## 캐시와 윈도우

Pipeline의 「캐시와 윈도우」에서 예제를 선택해 삽입하고 입력 필드에 맞게 수정한 뒤 샘플을 실행합니다. `cache_get`, `cache_set`, `point_window`, `window_hit`, `agg_create`, `agg_metric`은 `lookup()`, 조건, 라우팅과 함께 사용할 수 있습니다.

제한된 메모리는 **Worker × 흐름 게시 버전 × 입력 데이터 유형**별로 격리되며 같은 범위에서 배치 간 공유됩니다. Worker 재시작이나 이동 시 초기화됩니다. 전역 중복 제거, Worker 간 집계 또는 정확히 한 번 처리를 보장하지 않습니다. 다시 게시하면 새 상태를 사용하며 이전 버전은 수신된 입력을 처리한 뒤 마지막 미완료 집계를 출력합니다. 중지할 때도 같습니다. 1시간 동안 입력 처리에 성공하지 않은 범위는 남은 집계를 출력하고 회수하며, 적중하지 않은 문맥은 버립니다. 흐름을 삭제하면 메모리도 제거됩니다.

미리보기는 매번 별도의 새 상태를 사용하고 샘플 종료 시 미완료 집계를 출력합니다(`stateful_preview=true`). 실행 상태에 접근하지 않습니다. 시간 간격, 배치 간 상태, 재시작 동작은 게시된 흐름과 실제 대상으로 검증하세요.

### 윈도우 메트릭 집계

`agg_create(bucket, on_interval="60s", on_count=0, keep_value=false, const_tags=nil, category="M")`는 버킷을 정의하고 시간 또는 기록 수 조건이 충족되면 출력합니다. `"0s"`는 시간 조건을, `0`은 기록 수 조건을 끄지만 둘 다 끌 수는 없습니다. `agg_metric()` 호출 횟수와 무관하게 기여한 기록은 버킷당 한 번만 계산합니다. 개수는 그룹별이 아닌 버킷 전체 기준입니다. 이벤트 시간이 아닌 Worker 처리 시간을 사용합니다. 유휴 상태에서도 약 300ms마다 검사하며 부하로 지연될 수 있습니다.

`agg_metric(bucket, new_field, agg_fn, agg_by, agg_field, category="M")`는 `sum/avg/min/max/set`을 지원하며 `set`은 마지막 값입니다. 그룹 필드나 Tag는 문자열, 집계 입력은 숫자여야 하며 텍스트는 명시적으로 변환해야 합니다. float64 계산이므로 큰 정수나 정확한 소수의 정밀도는 보장하지 않습니다. 버킷 이름은 측정명, 그룹 값은 Tag가 됩니다. `"M"` 또는 `"metric"`은 메트릭을 출력하며 `const_tags`로 고정 문자열 Tag를 추가합니다. 원본 기록은 `drop()`으로 명시적으로 제거하지 않으면 유지됩니다.

### 용량과 실패 동작

| 항목 | 한도 |
|---|---|
| 상태 예산 | 범위당 8 MiB, Worker의 커밋된 상태 64 MiB, 128개 범위 |
| 캐시 | 4,096개 키, 키 1–1,024바이트, 값 64 KiB, TTL 1–3,600초(기본 100) |
| 문맥 | 256개 그룹, before/after 각각 0–128(동시에 0 불가), 키 1–8개, 키 1 KiB·값 4 KiB |
| 집계 | 버킷 16개, 버킷당 그룹 4,096개, 그룹당 필드 64개, 그룹 키 1–8개, 키/출력 필드 256바이트·그룹 값 4 KiB |
| 조건 | 1초–1시간, 1–1,000,000개 기록, 버킷 이름 256바이트 |
| 고정 Tag | 32개, 키 256바이트·값 4 KiB |

예산은 문자열, Point, 인덱스 비용의 추정치이며 RSS 한도가 아닙니다. 최대 8개 병렬 배치의 후보 상태, 디코딩과 출력도 임시 메모리를 사용합니다. 잘못된 인수·누락된 키·타입 오류·범위별 8 MiB 초과는 입력을 해제합니다. Worker 공용 바이트나 범위 수 부족은 입력을 유지하고 자원 회수 후 재시도합니다.

모든 CDC 청크를 포함한 전체 배치 결과가 큐에 저장된 후에만 상태를 커밋합니다. 중간 실패는 부분 변경을 남기지 않습니다. 타이머 출력 저장 실패 시 윈도우를 유지하고 재시도할 때까지 Worker 오류를 표시합니다. 큐에 저장된 출력은 일반 영구 큐로 재전송되고 재시작 후 복구되며 다시 집계되지 않습니다. 메모리의 캐시, 문맥, 집계는 백업되지 않고 재시작 시 손실됩니다. 수신됐지만 미처리된 입력은 빈 상태로 재개되므로 중단 없이 실행한 결과와 다를 수 있습니다.

Worker 드레인과 흐름 삭제는 진행 중인 처리와 최종 집계 전송 완료를 기다립니다. 최종 윈도우를 큐에 저장할 수 없으면 영구 큐가 비어 있어도 완료 확인이나 흐름 삭제를 허용하지 않고 윈도우를 유지하며 재시도합니다. 프로세스 종료는 메모리 상태를 초기화하므로 종료 전 온라인 드레인을 대신하지 않습니다.

수락된 SQL CDC 입력은 제한된 청크로 디코딩하고 해당 입력 전체 성공 후 원자적으로 대체합니다. 32 MiB를 넘는 PostgreSQL/MySQL 트랜잭션은 여러 입력으로 나뉘며 Pipeline은 입력별로 커밋하고 공통 인계 확인은 모든 입력 완료를 기다립니다.

서로 다른 흐름, 게시 버전 또는 데이터 유형의 상태 범위는 다른 범위가 디스크에 커밋하는 동안에도 처리할 수 있습니다. 각 범위의 처리 순서는 유지하며 큐 커밋 성공 후에만 후보 상태가 적용됩니다. 동시 증가분은 Worker 공유 예산을 먼저 예약하고 실패 시 해제합니다. 범위별 8 MiB, Worker 합계 64 MiB 및 휘발성 상태와 종료 전 명시적 온라인 비우기 제약은 유지됩니다.


## 수신, 재시도 및 리소스 경계

컨텍스트 창은 그룹별 마지막 입력 후 한 시간이 지나면 회수되며 다른 그룹 트래픽으로 연장되지 않습니다. keep_value 그룹도 한 시간 유휴 후 회수합니다. 아직 출력하지 않은 값은 정상 영속 출력으로 부분 집계를 만든 뒤 회수하며, 개수 전용 버킷이 임계값 미만이어도 같습니다. 같은 키의 후속 입력은 새 누계입니다. 활성 창256개, 버킷별4096그룹과 메모리 예산은 유지합니다. 변경한 집계 그룹만 복사하며 취소/영속화 실패 시 후보 상태를 게시하지 않습니다. 컴파일 캐시는 항목별로 제거합니다.


Pipeline 디버그, 연결 진단, 저장 및 게시는 열린 고급 JSON 편집을 포함한 현재 소스 설정을 사용합니다. 고급 JSON이 유효하지 않으면 이전 설정으로 되돌아가지 않고 디버그를 차단합니다.


일반 Pipeline 출력과 주기적·최종 집계 윈도는 대상별로 바이트 및 배치 할당량 안에서 독립적으로 준비합니다. 과대 분기나 같은 채널의 오래된 출력에 대한 용량 처리가 여유 있는 다른 채널을 실패시키지 않습니다. 단일 과대 분기는 기존 적체를 삭제하지 않습니다. 유지할 출력, 용량 폐기 횟수, 입력 완료 및 커서 확인은 하나의 WAL 트랜잭션으로 저장합니다. 전송 중인 데이터는 보호합니다. 준비 중 할당량이 바뀌면 다시 준비하고, 쓰기 실패 시 입력이나 윈도를 유지하며 카운터와 커서를 진행하지 않습니다.

용량 예약이 설치되지 않은 이전 입력에는 기존 전체 출력 준비 예산을 적용합니다. 초과하면 `pipeline/output_limit`으로 입력을 종료하고 처리 실패를 영구 기록하며 순서대로 확인을 완료합니다. 저장소 장애로 무한 재시도하지 않습니다. 격리 할당량이 설치된 경우 과대 분기는 해당 채널 안에서만 폐기하고 계수합니다. 준비 중 할당량이 바뀌면 입력이나 윈도를 유지한 채 다시 준비하고 디버그 로그만 기록합니다. 실제 저장소 오류에서는 계속 데이터를 유지하고 오류를 보고합니다.

할당량 축소 후 배출 중이 아닌 채널에서 출력 접두부를 잘라내면 FIFO 순서상 더 오래된 미전송 적체도 함께 제거합니다. 주기적·최종 윈도는 기존 적체 뒤에 오므로 유지할 윈도 접미부와 일부 이전 데이터가 할당량에 들어가더라도 해당 채널의 더 오래된 제거 가능한 적체를 모두 종료합니다. 이는 최신 FIFO 접미부를 유지하기 위한 규칙입니다. 단일 과대 분기는 이 경계를 진행하거나 이전 적체를 제거하지 않습니다. 전송 중인 분기는 항상 보호하며, 할당량을 차지하고 있을 때는 같은 채널의 새 분기만 폐기합니다. 여유가 있는 다른 대상은 막지 않습니다.

Pipeline 미리보기와 게시의 컴파일 오류는 행과 열을 유지합니다. 알 수 없는 함수, 잘못된 인수 개수, 호환되지 않는 형식을 식별하면 안전한 이유도 반환합니다(`pipeline_compile_error_reason` 및 중첩 원인 코드). 그 외에는 `pipeline_compile_error`, 위치가 없으면 `pipeline_compile_failed`를 사용합니다. 실행 오류는 `pipeline_runtime_error`, 위치가 없으면 `pipeline_runtime_failed`입니다. 위치는 `params[0]`, `params[1]`에, 이유는 `causes`에 포함됩니다. 화면은 각 계층을 번역하며 일반 텍스트에도 안전한 설명이 표시됩니다. 스크립트 리터럴, 입력값, 외부 라이브러리의 원본 오류는 노출하지 않습니다.
