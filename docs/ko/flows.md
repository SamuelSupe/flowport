# 데이터 흐름 구성과 게시

[FlowPorts 0.5.3](../../README.ko.md) · [Docs](../index.md) · [Website](https://flowport.pages.dev/ko/docs/)

미완성 초안은 소스, 대상 또는 대상 할당량이 없어도 저장할 수 있습니다. 명시한 할당량은 양수이고 합계 예산 이내여야 합니다. 저장은 수집을 시작하거나 실행 버전을 변경하지 않습니다. 게시에는 완전한 대상과 해당 할당량이 필요합니다. 자동 할당은 게시 시 확정되며 대상 추가로 수동 할당량이 자동 재분배되지는 않습니다.

게시 후 실행 보기의 전달 검증을 사용하세요. 현재 버전 설치, 소스 준비, 최신 보고서 및 적체 해소를 기다린 뒤 검증을 시작하고 업스트림에서 실제 데이터를 보냅니다. 지원되는 HTTP 및 DataKit 소스는 게시된 Token으로 바꿀 자리 표시자가 포함된 예제를 제공합니다. 새 수신 배치, 성공적으로 처리된 배치 및 모든 대상의 확인 증가분을 비교합니다. 각 경로에 맞는 샘플을 보내고 하위 내용을 확인하세요. 자동 전송이나 개별 레코드 추적은 하지 않습니다. 오래되거나 연결이 끊긴 보고서는 전달을 확인할 수 없습니다. 버전, Worker 배치, 프로세스 또는 카운터가 변경되면 다시 검증해야 합니다. 새로고침이나 범위 변경도 검증을 초기화합니다. 프로토콜 확인은 하위 업무 처리 완료를 뜻하지 않습니다.

> **0.5.0 정책 변경:** 아래의 보관 및 재시도는 새 채널 한도(기본 5회)까지입니다. 소진 시 미확인 데이터를 자동 폐기하고 최소 60초 후 단일 배치를 시험 전송합니다. 기존 횟수는 유지합니다. 관련 노드를 모두 프로토콜 v8로 업그레이드하세요. [전송 정책](https://flowport.pages.dev/ko/docs/delivery/)을 참고하세요.


편집 화면과 실행 보기 상단에 데이터 흐름 ID와 복사 기능이 표시됩니다. 로그인한 관리자는 수집 토큰(Vector 포함)을 직접 표시, 숨기기, 복사할 수 있습니다. 초안과 게시된 자격 증명은 분리되며 초안 변경은 게시 및 Worker 설치 후 적용됩니다. 토큰은 실행 보기의 집계 범위에서만 표시되고 개별 Worker에서는 표시되지 않습니다. 다른 상위 서비스 자격 증명은 마스킹됩니다. 일반 조회와 내보내기는 계속 비밀 값을 숨기며 API Key와 MCP로 수집 토큰을 조회할 수 없습니다.

최초 게시 전 Overview에서 첫 흐름 만들기 또는 설정 계속을 선택할 수 있습니다. 템플릿은 소스 설정부터 열리며 스크립트와 샘플을 유지합니다. 변환이 필요 없으면 다음: 전송 대상으로 진행하고 필요하면 선택 사항인 처리 규칙을 추가하세요. 흐름 안에서 대상을 추가하면 자동 선택되며 소스 설정과 스크립트가 유지됩니다.

현재 흐름으로 미리 보면 설정된 measurement(기본값: Source 유형)와 실행 시의 source_type, collectway_flow 태그를 사용합니다. 샘플은 소스에서 디코딩된 레코드를 나타내야 합니다. 미리 보기는 상위 서비스에 연결하거나 데이터를 전송하지 않습니다.

요약에는 최신 게시 설정을 표시하며 Worker를 선택하면 해당 노드에 설치된 파이프라인을 표시합니다. 게시와 설치 상태는 별도로 표시되며 대기 데이터 수에는 이전 버전도 포함됩니다.

편집기는 저장하지 않은 변경 사항과 저장 또는 게시 진행 상태를 표시합니다. 게시 후 실행 보기가 바로 열리므로 목록에서 다시 열지 않고 설정 적용 상태, Worker 설치 버전, 실제 전송을 확인할 수 있습니다. 흐름 목록의 버튼은 수신 중지와 수신 재개입니다. 수신 중지는 새 입력만 중지하며 대기 데이터의 처리 및 전송은 계속됩니다. 대상 장애로 수신이 자동 중지되지는 않습니다.

편집기 상단에서 초안 저장 → 흐름 게시 → Worker 설치 순서로 적용 단계를 설명합니다. 저장은 변경 사항만 보관합니다. 게시 후 실행 보기에서 설치된 버전을 확인하고 실제 전송으로 데이터 도착을 확인하세요. 대상 저장 후 참조 흐름과 설정 적용 상태가 바로 열리므로 각 흐름의 초안을 확인하고 게시할 수 있습니다. 대상 이름만 변경한 경우 다시 게시할 필요가 없습니다. 마지막 전송 대상 단계 하단에도 저장 후 게시가 있어 검토 후 상단으로 돌아가지 않고 제출할 수 있습니다. 저장 또는 게시 실패 시 상단에서 구체적인 오류를 표시합니다.

흐름에는 Source, 유형별 Pipeline, 기본 대상, 선택 Tag 라우팅, 실행 위치와 큐 용량이 있습니다. 게시하면 변경 불가능한 버전을 비동기로 Worker에 설치합니다. 초안은 실행 버전과 독립입니다. 저장 전 연결 테스트는 실제 Worker에서 수행하고 Pipeline 샘플과 구분합니다. [진단](https://flowport.pages.dev/ko/docs/#configure)을 참고하세요.

## Source와 수집 설정

이름, 흐름 ID, Source 유형/표시 이름으로 검색하고 새 흐름에서 수집 방식/지원 신호를 필터링합니다. 푸시는 토큰/리스너, 소비는 큐/토픽과 인증, 폴링은 완전한 URL이 필요합니다.

고급 JSON은 전체 Source 구성의 완전한 객체여야 합니다. 컨테이너 리스너는 보통 0.0.0.0과 매핑 포트를 사용합니다. ********를 유지하면 같은 유형의 비밀 값을 보존하고 새 값을 입력해 게시하면 교체합니다. 유형 전환에는 연결을 다시 구성합니다. [Source](https://flowport.pages.dev/ko/docs/integrations/)를 참고하세요.

## 처리 규칙

로그, 지표, 추적 등 신호마다 독립 스크립트를 선택합니다. 빈 스크립트는 통과하며 DataKit은 15개 유형을 지원합니다. 샘플 디버깅은 디코딩 Point, 출력, 필터링, 유형, 태그, 원시 JSON을 보여주며 하위에 보내지 않습니다. 입력/스크립트/유형을 바꾸면 이전 결과가 오래된 것으로 표시됩니다. 닫으면 입력과 결과를 유지한 채 편집으로 돌아갑니다. [Pipeline](pipeline.md)을 참고하세요.

## 기본 대상과 조합 라우팅

여러 기본 대상에 Point를 복제해 독립 확인/재시도합니다. 서로 다른 대상은 최대 32개입니다. 대상 없는 초안은 저장할 수 있지만 게시할 수 없습니다.

eq, neq, exists, not_exists 및 중첩 AND/OR를 사용합니다. 첫 일치가 기본 집합을 대체하고 미일치는 기본을 사용합니다. 규칙마다 하나 이상의 대상을 선택합니다. 항상 저장할 대상은 기본과 모든 규칙에 포함합니다. 처리 후 Tag를 읽으며 일반 필드는 set_tag로 변환합니다. 대소문자를 구별하고 자동 공백 제거는 없습니다. signals 필터가 다음 규칙을 실행하지 않습니다. [라우팅](https://flowport.pages.dev/ko/docs/pipeline/)을 참고하세요.

현재 실패 처리 및 마이그레이션: [FlowPort](https://flowport.pages.dev/ko/docs/delivery/).

## 위치와 용량

자동 배치 또는 허용 Worker를 지정합니다. 푸시/공유 소비는 여러 노드, 폴링 등은 독점 임대를 사용합니다. 네트워크, TLS 파일, 클라우드 인증은 실제 Worker에서 사용할 수 있어야 합니다.

새 흐름은 Worker마다 기본 256 MiB와 내부 배치 500개를 입력 및 각 대상에 고정 할당합니다. 노드는 기본 10 GiB 및 최대 내부 배치 10000개이며 예약과 과거 사용량이 한도 내에 있어야 합니다. 물리 로그와 체크포인트에는 추가 공간이 필요합니다. 수신 확인은 로컬 영구 큐 저장만 의미합니다. 대상별 재시도는 최초 시도를 제외하고 기본 5회이며 0~100회로 설정할 수 있습니다. 소진 시 미확인 데이터를 영구 삭제하며 데드 레터나 수동 재생은 없습니다. 입력이 가득 차면 새 데이터를 거부하고 출력이 가득 차면 해당 채널 내에서만 FIFO로 제거합니다. 축소 시 기존 적체를 유지한 채 해소를 기다립니다. 처리 실패도 입력을 해제할 수 있습니다. 게시 성공만으로 Worker 설치나 다운스트림 수신을 증명할 수 없습니다. 실제 하위 내용을 확인하세요.

## 저장, 게시와 버전

초안 저장은 편집만 보관합니다. 게시는 검증과 새 버전 배포, 중지는 새 입력 중지, 시작은 마지막 게시 버전 재개입니다. 대상 저장 후 참조 흐름을 재게시해야 새 입력에 적용합니다.

동기화 중 희망/실제 버전, Source 상태와 오류를 확인하세요. 게시 성공만으로 수집을 입증하지 않습니다. 버전 충돌은 다시 읽고 검토하며 미저장 이탈에는 확인이 표시됩니다.

## 실행 그래프에서 구성

연필로 Source, Pipeline/유형, Tag 규칙 또는 해당 Destination을 엽니다. 클릭은 저장/게시하지 않습니다. 그래프는 게시 버전이고 편집기는 최신 초안입니다. 돌아오면 Worker, 애니메이션, 스크롤과 열기 버튼 초점이 복원됩니다. 편집 중 그래프 조회만 중지하고 실제 수집은 계속합니다. 늦은 응답으로 이탈 후 편집기를 다시 열지 않습니다. 스크립트 목록은 키보드 스크롤을 지원합니다.

## 중지와 삭제

먼저 중지하고 모든 관련 Worker의 최신 중지/정상 빈 큐 보고를 기다립니다. 실행 중, 대기, 실패, 누락 보고 또는 과거 관련 노드 오프라인이면 삭제할 수 없습니다. 전송 실패는 용량 내에서 자동 재시도하고 이전 격리 데이터는 중지 후 명시적으로 내보내거나 정리합니다. 정상 배출 후 제거한 Worker는 마지막 빈 큐 확인을 쓸 수 있으며 강제 제거의 알 수 없는 데이터를 빈 것으로 처리하지 않습니다. [클러스터](https://flowport.pages.dev/ko/docs/cluster/)와 [문제 해결](https://flowport.pages.dev/ko/docs/delivery/)을 참고하세요.

수신 확인은 로컬 영구 큐 저장만 의미합니다. 대상별 재시도는 최초 시도를 제외하고 기본 5회이며 0~100회로 설정할 수 있습니다. 소진 시 미확인 데이터를 영구 삭제하며 데드 레터나 수동 재생은 없습니다. 입력이 가득 차면 새 데이터를 거부하고 출력이 가득 차면 해당 채널 내에서만 FIFO로 제거합니다. 축소 시 기존 적체를 유지한 채 해소를 기다립니다. 처리 실패도 입력을 해제할 수 있습니다. 게시 성공만으로 Worker 설치나 다운스트림 수신을 증명할 수 없습니다. 실제 하위 내용을 확인하세요.

게시된 데이터 흐름 ID는 삭제 후에도 과거 리소스 식별자로 유지되므로 재사용할 수 없습니다. 새 흐름에는 새 ID를 사용하여 Worker 커서, 임대 기록 또는 카운터를 이어받아 초기 수집을 건너뛰지 않도록 합니다. 동일 흐름의 중지 후 재시작은 저장된 진행 상태에서 계속됩니다. 게시한 적 없는 초안은 삭제 후 ID를 재사용할 수 있습니다.

초안에는 독립적인 `draft_revision`이 있습니다. 새로 만들 때는 0을 사용하고, 수정할 때는 읽은 `revision`과 `draft_revision`을 모두 반환하세요. 저장 성공 시 새 초안 버전이 반환됩니다. 게시 요청 본문에는 저장 응답의 `draft_revision`이 필요합니다. 없으면 400, 초안이 변경되었으면 409를 반환하며 다른 편집자의 변경을 게시하지 않습니다. Source 프로토콜을 바꾸면 민감한 설정을 다시 입력해야 합니다. 흐름 목록의 게시 이력에서 페이지별 조회와 설정 비교를 할 수 있으며 이전 버전을 초안으로 복원할 수 있습니다. 복원만으로 실행 중인 버전은 바뀌지 않습니다. 검토 후 정상 게시 절차를 사용하며 현재 전송 대상의 주소와 자격 증명을 적용합니다.

제거된 Worker의 과거 수신, 전송 및 대상별 카운터는 목록과 실행 화면에 동일하게 유지되며 표본은 오프라인으로 표시됩니다. 강제 제거된 노드의 큐 상태가 알 수 없으면 흐름 삭제는 계속 차단됩니다. 노드가 영구적으로 손실되었다면 흐름을 중지하고 업스트림과 로드 밸런서에서 제외한 다음 흐름 목록의 노드 적체 처리에서 제거된 노드를 선택하고 전체 흐름 ID를 입력하세요. `POST /flows/{id}/abandon-worker`에는 `worker`와 흐름 ID와 동일한 `confirm`을 지정합니다. 해당 흐름에 대한 해당 노드의 삭제 차단만 해제하며 디스크와 마지막 보고서는 변경하지 않고 다른 노드의 비우기 확인도 우회하지 않습니다. 결정은 영구 저장되고 강제 작업으로 감사 기록에 남습니다. `GET /flows/{id}/recovery`로 조회할 수 있습니다.

현재 실패 처리 및 마이그레이션: [FlowPort](https://flowport.pages.dev/ko/docs/delivery/).


0.1.19부터 전송을 시작한 뒤 응답 전에 FIFO로 제거된 분기도 실제 실패 또는 확인된 성공을 영구 집계하고 대상 상태를 갱신합니다. 페이로드를 복원하거나 제거 횟수를 취소하거나 수신 위치를 두 번 진행하지 않습니다. 같은 분기가 FIFO 제거와 확인된 전송 모두에 집계될 수 있으므로 두 수를 빼서 고유 입력 수를 계산할 수 없습니다. 유효한 연결의 늦은 성공은 해당 대상의 알림을 해제할 수 있습니다. 이전 게시 연결의 결과는 현재 상태를 바꾸지 못하며, 제거되어 적체가 없는 대상의 늦은 실패는 알림을 다시 만들지 않습니다.


## 0.1.21

참조 흐름을 다시 게시하고 Worker 설치를 기다리세요. 같은 대상 ID의 적체는 처리 결과를 유지하며 다음 재시도부터 새 연결을 사용합니다. 이전 진행 중 요청은 취소할 수 없으며 복구 시 중복이 발생할 수 있습니다.

저장된 대상 설정을 비교하며 저장하지 않은 편집은 제외합니다. 이름 변경은 다시 게시할 필요가 없습니다. 현재 연결이 설치된 Worker는 다음 재시도부터 사용하며 이전 진행 중 요청은 취소할 수 없습니다.

최근 삭제는 현재와 이전 4개 분 버킷을 집계하며 재시작 후에도 유지됩니다. 큐 시간은 최초 수신 시각입니다. 오프라인 노드의 마지막 샘플로 현재 보존 시간을 예측할 수 없습니다.

삭제 수는 로컬 입력 또는 대상 분기 단위이며 고유 입력 손실률로 환산할 수 없습니다. 대상 복사본과 배치 한도는 보존 범위를 줄입니다. 논리 할당량은 실제 디스크를 예약하지 않습니다.

현재 초안과 저장된 대상 신호 필터를 최대 100개 출력 포인트로 미리 봅니다. 연결하거나 쓰기 권한을 검증하지 않습니다. 일치하지 않으면 기본 대상을 사용하며 신호 필터링 후 다음 규칙으로 넘어가지 않습니다.

매개변수를 저장하고 참조 흐름을 재게시하여 설치한 뒤 새 입력과 같은 대상 ID 적체에 새 연결 적용。


## 0.1.24 리소스 및 기록 제한

흐름별 최신 100개 버전을 전체 암호화 스냅샷의 공통 64 MiB 예산 안에 유지합니다. 참조하지 않는 오래된 기록부터 회수하고 현재 버전, 정상／기존 격리 큐, 전송 중 작업, 관리자 승인／Worker 보고 버전은 보호하므로 개수 제한을 넘을 수 있습니다. 보호된 스냅샷만으로 예산이 차면 새 게시가 실패하고 기존 수신은 계속됩니다. 업그레이드 전 초과 참조도 유지합니다. 비워진 흐름을 삭제하면 전체 기록은 회수하고 ID 재사용을 막는 최소 정보만 남깁니다. 남아 있는 버전만 조회／복원할 수 있습니다. 실제 공간은 일반 로그 회수 시 해제되며 기존 실패 페이로드를 자동 삭제하지 않습니다. 이전에 할당된 원격 Worker는 로컬 정상 큐와 기존 실패 페이로드가 모두 비워진 뒤 삭제된 흐름 구성을 회수하며 오프라인 노드는 재연결 후 처리합니다.

현재 버전은 제어 프로토콜 v8와 체크포인트 형식 3을 사용하며 이전 형식 1/2를 읽습니다. 서비스를 중지하고 각 노드의 전체 데이터, master.key, Lookup 및 환경 설정을 백업한 뒤 관리 서버와 모든 Worker를 함께 업그레이드하세요. 다운그레이드는 업그레이드 전 전체 백업을 복원하고 이후 수신 데이터를 대조해야 하며 이전 실행 파일로 업그레이드된 디렉터리를 직접 열거나 덮어쓰면 안 됩니다.

## 시나리오 템플릿과 단일 흐름 가져오기/내보내기

새 흐름에서 빈 구성, 시나리오 템플릿 또는 설정 가져오기를 선택합니다. HTTP 로그 전달, 로그 수준별 라우팅, 60초 중복 제거, 오류 전후 로그, 윈도우 집계 메트릭 템플릿을 제공합니다. HTTP JSON 소스, 스크립트, 샘플이 미리 입력되며 소스를 변경할 수 있습니다. 인증 정보, 대상, Worker를 설정하고 Pipeline 샘플 디버깅 후 저장 및 게시하세요. 집계 대상은 metric을 지원해야 합니다. 캐시와 윈도우는 Worker, 게시 버전, 입력 유형별로 격리된 제한된 메모리를 사용하며 재시작 시 초기화됩니다.

흐름 목록에서 설정 내보내기를 클릭하고 저장된 초안 또는 최근 게시된 설정을 선택하여 JSON을 다운로드합니다. 저장하지 않은 편집은 제외됩니다. 형식은 `format: "flowport.flow"`, `version: 1`이며 소스 설정, 유형별 Pipeline, 기본/라우팅 대상 참조, Lookup 바인딩, 큐 용량, ACK 정책을 포함합니다. 공유 대상 연결, Lookup 내용과 동기화 인증 정보, Worker 배치, 큐, 수집 커서, 게시 이력, 메모리 상태는 제외되며 전체 백업을 대체하지 않습니다.

토큰, 비밀번호, headers, URL, 연결 문자열, 개인 키 등 민감한 연결 필드는 재귀적으로 제거하여 `removed_fields`에 표시합니다. 스크립트, SQL 및 사용자 지정 설정의 리터럴 값은 그대로 유지되므로 공유 전에 확인하세요. 가져올 때도 민감한 필드를 제거하며 `********`로 기존 인증 정보를 복구하지 않습니다.

가져오기 절차:

1. 대상 작업 공간에 필요한 전송 대상과 Lookup을 먼저 생성합니다. Lookup 데이터는 별도로 업로드하거나 동기화합니다.
2. 새 흐름 → 설정 가져오기에서 최대 2 MiB의 JSON을 선택합니다. 형식 버전, Source 유형, 구조를 확인하고 요약과 제거된 필드를 표시합니다.
3. 모든 기본/라우팅 대상과 Lookup 참조를 로컬 리소스에 명시적으로 연결합니다. 이름이나 ID가 같아도 자동 연결되지 않으며 공유 리소스를 생성하거나 덮어쓰지 않습니다.
4. 이름, 연결, 인증, Worker, 큐 용량, 규칙을 확인합니다. Lookup 자동 업데이트 정책과 고정 버전은 유지됩니다. 고정 버전이 선택한 리소스에 존재하고 호환되는지 Pipeline Lookup 패널에서 확인하거나 조정하세요.
5. 샘플을 실행하고 새 초안으로 저장한 뒤 명시적으로 게시합니다. 파일을 선택하거나 편집기로 이동해도 저장, 수집 시작, 원본 흐름 수정은 하지 않습니다. 새 ID를 사용하고 게시 및 실행 상태를 초기화합니다. 수집 진행 상태를 이어받지 않으므로 소비형 소스의 시작 위치를 확인하세요.

REST: `GET /api/v1/flows/{id}/export?configuration=draft|published`는 민감 정보를 제거한 패키지를 반환하며 기본값은 draft입니다. `POST /api/v1/flows/import-preview`는 전체 패키지를 받아 정규화된 설정과 완전한 의존성 목록을 반환하고 저장하지 않습니다. 의존성을 연결하고 새 Flow ID를 지정한 후 기존 초안 PUT 및 게시 POST를 사용합니다. 기존 인증과 2 MiB 관리 요청 제한을 따릅니다. 내보내기는 read, 가져오기 미리보기는 write 권한이 필요하며 저장과 게시는 기존 감사에 기록됩니다. MCP 도구는 `exportFlow`, `previewFlowImport`입니다. 시나리오 템플릿은 UI에서 제공하며 스크립트 의미는 [Pipeline 사용](pipeline.md)을 참고하세요.


가져오기 화면에 리소스 매핑 진행률이 표시되며 내용을 스크롤해도 작업 버튼은 계속 표시됩니다. 파일 확인 중에 취소하거나 다른 파일을 선택할 수 있으며 이전 응답이 새 선택을 덮어쓰지 않습니다. Lookup 목록은 현재 대화 상자가 열려 있는 동안만 재사용됩니다. 로딩에 실패하거나 리소스가 변경되면 리소스 새로고침을 선택하세요. 파일을 다시 업로드할 필요가 없으며 파일 요약과 선택한 전송 대상이 유지됩니다. 내보내기 대화 상자를 닫으면 완료되지 않은 다운로드 요청도 취소됩니다.

게시 이력에서 현재 초안과 선택한 버전의 소스, Pipeline, Lookup 바인딩, 대상, 라우팅, 큐 용량 및 Worker 배치를 비교합니다. 복원은 초안만 교체하며 검토 후 게시해야 실행 설정이 바뀝니다. 바인딩에 고정된 Lookup 데이터 버전도 확인하세요. 세션 만료 후 다시 로그인해도 이전 생성 대화 상자가 자동으로 열리지 않습니다.


편집기 상단에 ID, Token과 주요 작업을 표시합니다. 저장 및 게시 설명을 펼쳐 적용 단계를 확인할 수 있습니다. 저장은 초안만 갱신합니다. 게시 후 Worker 설치 버전과 실제 전달을 확인하세요.


대상이나 라우팅 구성을 완료하기 전에도 샘플 스크립트를 실행할 수 있습니다. 처리 결과는 반환하고 경로 미리 보기에서 라우팅 오류를 별도로 표시합니다. 구성을 완료한 뒤 다시 실행하세요. 게시는 전체 구성을 계속 검증합니다.


Pipeline 디버그, 연결 진단, 저장 및 게시는 열린 고급 JSON 편집을 포함한 현재 소스 설정을 사용합니다. 고급 JSON이 유효하지 않으면 이전 설정으로 되돌아가지 않고 디버그를 차단합니다.


게시 성공 알림은 설정이 저장되었음을 의미합니다. Worker 설치 완료 여부는 실행 보기의 설정 상태에서 확인하세요.

## 고정 용량 격리

편집 화면은 데이터 흐름 이름을 제목으로 사용하고 저장하지 않은 변경 사항, 저장된 초안, 실행 중인 설정을 구분합니다. 전송 대상 단계의 채널 용량 영역에는 총 예산, 할당량, 입력 및 출력 할당량을 함께 표시합니다. 각 영역 행에서 바이트와 배치 수를 편집합니다. 예산 초과나 누락된 할당량이 있으면 게시할 수 없으며, 축출과 축소 규칙은 펼쳐서 확인할 수 있습니다.

새 흐름의 기본값은 256 MiB와 500개 배치이며 저장된 작업 공간 기본값과 명시적 할당은 변경되지 않습니다. 고정 용량 격리만 지원합니다. 대상 설정에서 `queue_capacity.input`과 `queue_capacity.outputs`를 할당하고 저장 및 게시합니다. 새 게시에서 생략하면 입력과 모든 대상에 바이트 예산과 500개 배치를 균등 분배하며 편집 화면도 저장 시 초기값을 기록합니다. 기존 명시적 할당은 자동 변경하지 않습니다. 새 대상은 직접 할당해야 합니다. 단위는 Worker × 흐름 × 대상입니다. 영역 합계는 `queue_bytes`와 `queue_capacity.batches` 이내여야 합니다. 예약과 미이전 기존 데이터는 노드 바이트 한도 및 내부 10000개 배치 이내여야 합니다. 기본 흐름이 여러 개면 노드 배치 한도를 초과할 수 있으므로 할당량을 직접 줄여야 합니다. 자동으로 축소되지 않습니다. 미할당 용량은 어떤 채널에도 속하지 않으며 서로 빌리지 않습니다.

업그레이드 전에 각 Worker 백업 사본에서 `collectway -queue-capacity-preflight -data-dir <Worker백업사본> -queue-bytes <노드바이트예산>`을 실행하고 운영 데이터 디렉터리를 직접 지정하지 마세요. 사전 검사는 메타데이터 추정이며 페이로드 무결성이나 향후 배치를 보장하지 않습니다. 기존 불변 버전의 바이트 예산을 유지하고 Worker는 기본 500개 배치로 고정 예약을 시도합니다. 기존 예약은 재시작과 이후 업그레이드에서도 유지되며 새 대상은 명시적 할당이 필요합니다. 레코드 수가 없는 출력은 잠금 밖에서 최대 64개와 약 32 MiB씩 읽고 진행 상태를 저장합니다. 용량 부족, 대상 불일치 또는 읽기 오류 시 데이터를 보존하고 새 입력을 중단합니다. 상위 버퍼링은 소스에 따라 다릅니다. 재시작 전에 메모리 윈도를 비우세요. 프로토콜 v6과 v8은 호환되지 않으므로 조정된 업그레이드 중 수신이 중단될 수 있습니다. 게시가 Worker 설치 성공을 뜻하지는 않습니다. 중지된 흐름도 예약을 유지합니다.

기존 적체가 기본 영역 할당량을 초과하면 할당량과 사용량 중 큰 값으로 예약하고 축소 후 배출 상태로 전환합니다. 입력 초과 중에는 새 입력을 거부하며 출력 초과 중에는 기존 적체를 보존하고 해당 채널의 새 분기를 폐기 및 집계합니다. 사전 검사는 영역별 한도, 사용량 및 실제 예약을 표시하며 노드는 실제 예약을 수용해야 합니다. 활성 흐름이 Worker에서 이동하면 로컬 적체, 진행 중 요청 및 집계 윈도가 모두 끝난 뒤 예약을 해제하고 재배치 시 다시 예약합니다. 전체 비활성 흐름은 예약을 유지합니다. 관리 서버와 해당 Worker 모두 이 수정이 필요합니다. 이전 v8 Worker는 해제 지시를 무시합니다. 준비 기한은 페이로드 읽기 사이에 확인하므로 한 번의 디스크 읽기나 영구 커밋은 기한을 초과할 수 있습니다.

입력 영역이 가득 차면 출력을 제거하지 않고 새 입력을 거부합니다. HTTP/gRPC는 재시도 가능한 오류를 반환하고 확인 가능한 소스는 미확인 상태를 유지하며 UDP는 폐기를 집계합니다. DataKit, Firehose 및 CDC의 전체 요청/트랜잭션은 원자적으로 입장합니다. 커서 메타데이터 부족도 새 입력을 거부하며 기존 영수증의 모든 분기를 지우지 않습니다.

하나의 WAL 트랜잭션에서 입력을 제거하고 대상 출력을 추가하며 해당 채널의 원래 수신 순서에 따라 제거합니다. 분할, 복제, 재시도, 대기 및 전송 중 배치 모두 용량을 차지합니다. 너무 큰 단일 분기는 자신만 폐기하며 기존 적체를 비우지 않습니다. 전송 중 데이터는 보호하고 공간을 만들 수 없으면 새 분기를 버립니다. 용량 폐기는 전송 시도나 성공으로 집계하지 않으며 사전 저장된 레코드 수를 사용합니다. 모든 분기가 종료된 후 커서를 순서대로 진행하므로 CDC에서도 데이터 누락이 생길 수 있습니다.

축소는 기존 적체를 즉시 삭제하지 않습니다. 새 한도를 넘는 동안 배출 중으로 표시하고 새 출력은 가득 찬 상태로 처리합니다. 사용량이 줄어야 예약을 해제합니다. 삭제한 대상은 기존 입력, 출력 및 진행 중 요청이 끝날 때까지 제거 중입니다. 새 대상은 명시적 할당이 필요합니다. 확장/마이그레이션 사전 검사 실패 시 기존 설치 버전을 유지합니다. 공유 모드 복귀 전 큐를 비워야 합니다.

실행 상세에 Worker별 적용 버전, 사용량, 한도, 실제 예약, 가장 오래된 적체 시각 및 용량 폐기를 표시합니다. 용량 상태는 전달 상태와 별개이며 지속 제거는 최근 5분 내 폐기를 뜻합니다. 전송 성공으로 즉시 해제되지 않습니다. 오래되거나 오프라인인 보고는 마지막 보고로 표시합니다. 제어 프로토콜 v8이므로 관리 노드와 관련 Worker를 모두 업그레이드해야 합니다. 관리 노드 게시 성공만으로 Worker 적용을 확정할 수 없습니다.

격리는 논리 용량과 제거 범위에만 적용됩니다. 디스크, CPU, 네트워크 및 Store 쓰기는 공유하므로 디스크 부족은 노드 전체 입력을 중단시킬 수 있습니다. 재시작 시 용량, 순서, 재시도 횟수와 이력을 유지합니다.

용량 적용 상태는 영역 ID와 할당량 값을 비교하므로 JSON 키 순서의 영향을 받지 않습니다. 실행 값에는 대상 이름을 표시합니다. 종료 중인 채널은 계속 예약 중인 할당량을 표시합니다.
